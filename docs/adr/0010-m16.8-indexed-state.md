# ADR 0010: bounded IndexedState reads for MIN/MAX

Status: accepted; implemented and re-proved in M16.8 and M16.8.1 on
PostgreSQL 17.10 and 18.4.

## Context

M16.5 established correct MIN/MAX semantics with positive per-value
multiplicity in `shiba_internal.graph_node_state`. A straightforward read of a
group loaded every value in the partition into a Rust `BTreeMap`. That made
memory and query work grow with historical partition cardinality even when a
transaction touched one row. Keeping only the current extreme would be
incorrect because deleting it must reveal the next value and duplicate values
must retract one copy at a time.

## Decision

Keep `graph_node_state` as the sole durable state authority and Runtime as its
sole writer. Extend the existing `StateReadSet` with a request-only
`StateRange`:

```text
(node_id, namespace, partition_key, direction, limit, order_key_version)
```

MIN/MAX requests contain exact keys for every non-NULL value touched by the
current batch and one ordered range per affected group/call. The range limit is
exactly `1 + touched_distinct_count` for that group and call. The proof is
local: after all touched values are removed or replaced, a new extreme can
only be a touched value or one of the first `1 + K` pre-state values in the
required direction. Exact/range duplicate rows are removed before creating the
validated transaction-local snapshot. Full-partition reads are not an extrema
fallback.

The version-1 Int8 order key is derived by flipping the sign bit of the
two's-complement big-endian `i64` bytes. Bytewise ascending order is therefore
signed numeric order, including `i64::MIN`, `-1`, `0`, `1`, and `i64::MAX`.
`item_key_payload` remains the canonical identity; `item_order_key` is checked
derived data. A missing, stale, non-eight-byte, non-Int8, or unknown-version
order key fails closed. PostgreSQL serves ranges through the partial B-tree
`graph_node_state_ordered_item` with ASC/DESC `LIMIT` and locks candidates in
the same processor transaction.

The existing graph budget is the single resource authority. It charges exact
keys, range candidates, partition entries, loaded rows, state payload bytes,
state/result mutations and estimated work bytes before a transition is
constructed. Any budget, codec, order-key, arithmetic, sink or backend failure
rolls back source state, graph state, complete results and continuation; no ACK
is authorized. The range candidate window is never persisted as a log or
second state representation.

## M16.8.1 range contract hardening

The request-only range protocol now rejects duplicate or ambiguous
`(node, namespace, partition, direction)` requests before SQL. Runtime tags
every returned candidate with its range index and validates the ordered result
count, direction, partition coordinates and derived Int8 order key before
flattening a transaction-local `StateSnapshot`. The per-range non-exact
candidate count must be at most the declared limit; an exact-key overlap is
counted once. A limit-plus-one result, missing provenance, duplicate candidate,
wrong order or stale order key fails closed before operator evaluation.

Production and EXPLAIN tests share the same `WITH ranges` / `CROSS JOIN
LATERAL` / dynamic `LIMIT` / `FOR UPDATE` query builder. No durable authority,
writer, table, fallback or ACK rule changed. This hardening does not authorize
TopK or any new function family.

## Evidence and consequences

Database-free tests cover order vectors, stale/duplicate/malformed entries,
exact/range overlap, per-range limits and aggregate differential/retraction
semantics. The M16.8 PG gate creates 100,000 distinct values, uses ten 10,000-row
bootstrap batches, then deletes the current minimum through the production
receiver/Apply/ACK path. PG17.10 and PG18.4 both show the ordered index and two
candidate rows in the production-shaped `EXPLAIN (ANALYZE)`; the full state
authority remains in the database while each transaction's loaded candidate
set is bounded.

This ADR does not authorize TopK, AVG, variance/stddev, Numeric, DISTINCT,
window functions, joins, new SQL syntax, a new state table, a second writer,
or a full-partition fallback.
