## 1. 结论摘要

本次在真实 PostgreSQL 17.10 隔离集群上完成了 Shiba release 构建的首份性能基线。
最终结果与 PostgreSQL 从源表全量重算的 bag comparison 差异数为 **0**，
pgbench 失败事务为 **0**，PostgreSQL 日志无 `ERROR`、`FATAL`、`PANIC` 或
`WARNING`。

最重要的结论有三点：

1. **读性能收益显著。** 对随机 group 的等价聚合点查，Shiba 结果表平均
   0.040 ms / 201,667 TPS；源表即时聚合为 13.592 ms / 588 TPS。延迟降低约
   **339.8 倍**，吞吐提高约 **342.8 倍**。全量读取 10,000 个聚合结果时，
   Shiba 为 0.509 ms，源表重算为 25.515 ms，约 **50.1 倍**。
2. **主要写入瓶颈是“每 25 ms 最多消费一个源事务”。** 400 个事务、每事务
   10 行的突发写入只需 61 ms 进入源表，但结果完全追平共需 11.165 s，
   即约 **35.8 commits/s、358 rows/s**。这与 DAG worker 的 25 ms 固定等待
   和每轮只调用一次 `process_next_dag_transaction` 高度吻合，理论上限约
   40 commits/s。
3. **批量事务能显著摊薄提交开销。** 单个 20,000 行事务的 worker 应用速度
   为 4,945 rows/s，是 10 行小事务端到端速率的 **13.8 倍**。当前实现对
   事务大小敏感，优化时应优先让 worker 在一次唤醒中持续 drain 多个已就绪
   commit，并仅在 inbox 为空时等待。

因此，这份基线支持一个清晰的优化顺序：先消除 DAG executor 的固定轮询/
单提交节流，再降低 Router 的 100 ms 轮询延迟，之后才值得深入优化单行
operator apply 的 SQL/SPI 成本。

## 3. 测试方法

### 3.1 隔离与控制变量

- 每次运行使用 `initdb` 创建全新临时集群，测试结束立即停止并移除。
- baseline 与 Shiba 分属同一实例中的两个数据库，表结构、初始数据生成方式、
  pgbench SQL 和服务端配置一致。
- baseline 是没有安装 Shiba 的普通 PostgreSQL 表；Shiba 数据库创建一个
  grouped `COUNT(*) + SUM(amount)` streaming table。
- 查询测试在预热后的内存态执行，因此衡量的是 CPU/执行器成本，不是冷盘 I/O。
- 写入测试使用 4 clients、每 client 100 transactions、每 transaction 10 rows。
- 可见延迟使用 40 次串行唯一 group 插入，计算源提交附近时间戳到
  `view_progress.updated_at` 的差。
- 大事务测试先停 DAG worker，提交 20,000 行，确认 Router 已持久化 inbox，
  再启动 worker 并等待结果行计数追平。

### 3.2 正确性判定

压测结束后独立执行以下双向 `EXCEPT ALL`：

```sql
WITH expected AS (
  SELECT group_id,count(*)::bigint AS row_count,sum(amount)::bigint AS total_amount
  FROM bench_events GROUP BY group_id
),
actual AS (
  SELECT group_id,row_count::bigint,total_amount::bigint
  FROM shiba.bench_stats
)
(SELECT * FROM expected EXCEPT ALL SELECT * FROM actual)
UNION ALL
(SELECT * FROM actual EXCEPT ALL SELECT * FROM expected);
```

差异计数为 **0**。最终 source 为 324,040 行，result 为 10,140 行，
`dag_inbox` 为 0。

## 4. 结果

### 4.1 初始回填

| 指标 | 结果 |
|---|---:|
| 300,000 行 CTAS + 注册 + state build | 524.825 ms |
| 等效回填速率 | 571,619 rows/s |

这是内存态、中等规模、简单单表聚合的结果，不应外推到 join、window 或超出
内存的数据集。

### 4.2 读性能

| 等价查询 | 平均延迟 | TPS | PostgreSQL 平均 CPU | 峰值 RSS |
|---|---:|---:|---:|---:|
| 源表过滤并即时聚合 | 13.592 ms | 588 | 370.7% | 338.6 MiB |
| 查询 Shiba 结果表 | 0.040 ms | 201,667 | 508.6% | 230.5 MiB |

CPU 是每 200 ms 对 postmaster 及其直接子进程的 `%CPU` 求和；在多核 macOS
上可以超过 100%。Shiba 查询虽然总 CPU 更高，但同期完成的请求数约高
343 倍，因此单查询 CPU 成本显著更低。

`EXPLAIN (ANALYZE, BUFFERS)` 的全量结果：

| 查询 | Execution Time | Shared hits | 返回行 |
|---|---:|---:|---:|
| 源表 `GROUP BY` 重算 | 25.515 ms | 1,622 | 10,000 |
| Shiba 结果顺序扫描 | 0.509 ms | 64 | 10,000 |

所有块均命中 shared buffers，没有磁盘读取。

### 4.3 源写入与异步追平

| 指标 | 普通 PostgreSQL | 启用 Shiba | 变化 |
|---|---:|---:|---:|
| pgbench client latency | 0.114 ms | 0.355 ms | 3.11× |
| 源写入 TPS | 34,403 | 11,058 | -67.9% |
| 失败事务 | 0 | 0 | — |

该场景只有 400 个固定事务，整个 Shiba ingress 阶段为 61 ms，短于资源采样
周期，因而没有可用的写阶段 CPU/RSS 样本；该 TPS 更适合作为方向性回归指标，
不适合作为容量承诺。

Shiba 的异步端到端结果：

| 指标 | 结果 |
|---|---:|
| 4,000 行进入源表 | 61.199 ms |
| 4,000 行全部出现在结果中 | 11,165.336 ms |
| 端到端速率 | 358.252 rows/s |
| 等效事务消费率 | 35.825 commits/s |

这里的关键不是源表接收速度，而是事务积压的消化速度。代码中 DAG worker
每轮先等待 25 ms，再只处理最早的一个 commit；观测值接近这一结构给出的
40 commits/s 上限。

### 4.4 异步可见延迟

| 指标 | ms |
|---|---:|
| min | 19.180 |
| p50 | 58.982 |
| mean | 62.986 |
| p95 | 82.576 |
| p99 | 82.681 |
| max | 94.689 |

样本是串行、系统无积压时的 commit-to-apply 时间，不包含应用侧下一次查询
轮询间隔。结果与 Router 100 ms 及 DAG executor 25 ms 的轮询周期相符。

### 4.5 单个大事务

| 指标 | 结果 |
|---|---:|
| 20,000 行源事务提交耗时 | 271.576 ms |
| worker 应用耗时 | 4,044.180 ms |
| worker 应用速率 | 4,945.378 rows/s |

大事务避免了对每个小事务支付一次 25 ms 调度等待，但 20,000 个 delta 仍在
一个数据库事务内串行应用。这个结果说明“commit 调度”是当前小事务负载的
第一瓶颈，同时单行 apply 仍有约 0.20 ms/row 的后续优化空间。

### 4.6 空间

| 对象 | 大小 |
|---|---:|
| source table | 13.73 MiB |
| public result table | 1.88 MiB |
| `shiba_internal` relations | 10.16 MiB |
| database total | 33.79 MiB |

内部关系约为 source table 大小的 74.0%。这个数字包含 extension catalog、
indexes 和 operator state，且只代表单聚合 DAG。

最终 `pending_wal_bytes` 为 23,836,056，但 inbox 已清空且结果完全正确。
该字段按 `pg_current_wal_lsn - confirmed_flush_lsn` 计算，会包含 Shiba 自身
写 state/result 产生、但不属于 publication 的 WAL；在没有后续 source
事务推进 slot 时，它不能直接解释为“尚未应用的业务 WAL”。后续可考虑把
这一观测口径拆成 slot retention、router inbox 和 DAG apply lag。

## 5. 瓶颈判断与优化优先级

### P0：DAG worker 调度

证据：

- 固定等待 25 ms；
- 每轮只处理一个 commit；
- 实测 35.825 commits/s，接近理论 40 commits/s；
- 将 4,000 行拆为 400 个 commit 时只有 358 rows/s，而单个 20,000 行
  commit 达到 4,945 rows/s。

建议的首个优化实验：

1. `process_next_dag_transaction` 返回“是否处理到数据”；
2. inbox 非空时连续处理多个 commit，直至达到时间/行数预算；
3. 仅在无数据时 `wait_latch`；
4. 保持每个源 commit 的原子性和当前 LSN 顺序；
5. 使用本报告的 400 小事务场景验证 commits/s、p95、CPU 与正确性。

### P1：Router 唤醒与批处理

Router 固定等待 100 ms，并每轮最多读取 2,048 条 logical messages。
空载 p95 为 82.576 ms，说明 Router 周期已直接进入用户可见延迟。可评估
基于 latch 的主动唤醒、忙时连续 drain、空闲时退避，以及记录每轮
messages/commits/bytes。

### P2：单 delta apply 成本

大事务约 4,945 rows/s，说明调度瓶颈消除后，逐 row JSON decode、SPI 调用、
state upsert 和 sink update 会成为下一瓶颈。后续应分别测 aggregate、
distinct、join、TopN、window，避免用 aggregate 结论替代所有 operator。

## 6. 可对比性规则

未来优化前后必须满足：

- 同一 benchmark workload checksum、同一 PostgreSQL 配置和相同参数；
- 同机、相同电源/温控状态，关闭明显后台负载；
- 每个 revision 至少 3 次，交替顺序运行，比较中位数而不是最佳值；
- correctness difference 必须为 0，failed transactions 必须为 0；
- inbox 未清空、日志存在数据库错误或 workload 参数不同的 run 不参与比较；
- 主要门禁建议：目标指标变化超过 10% 才视作可信改善/回退，5%–10% 需增加
  重复次数，低于 5% 默认视为噪声。

复现命令：

```bash
SHIBA_PERF_RUN_ID=baseline-replay ./scripts/performance-benchmark.sh
```

结果目录中的 `workload/` 是审计快照；如未来 harness 已变化，需要精确复放
本次驱动，应先将该快照中的脚本和 SQL 恢复到仓库对应位置，再从仓库根目录
执行。不要直接在结果目录运行脚本，因为它按自身位置解析 repository root。

## 7. 局限性

- 当前是单次基线，不包含跨 run 方差；优化验收时应补足至少 3 次。
- 数据集为 300,000 行且完全命中缓存，没有覆盖冷启动、磁盘饱和或 checkpoint
  抖动。
- 只测试一个 grouped aggregate DAG，没有覆盖多 DAG 扇出、join、window、
  TopN、update/delete 或长时间 soak。
- pgbench 与 PostgreSQL 位于同一台机器，通过 Unix socket 通信；结果不包含
  网络延迟。
- 写 TPS 固定计数场景过短，缺少 CPU/RSS 样本；可靠指标是其原始记录和
  端到端 drain 时间，不应直接外推为生产持续吞吐。
